# CLAUDE.md — Atlas V2

## Project Overview

Atlas is a marketing signal optimisation and tracking infrastructure platform for agencies, consultancies, and SMB marketers. Hosted at atlas.vimi.digital.

---

## Features

- **Journey Builder** — Multi-step wizard generating GTM container JSON. Business types incl. `b2b_lead_gen` (7-stage template); stages carry `proxy_value_gbp` + `buyer_intent_level`.
- **AI Planning Mode** — Browserbase/Playwright scan → Claude analysis → tagging recommendations, PII detection, GTM container + implementation guide (GCLID/UTM capture, CRM mapping, Enhanced Conversions for Leads). Approved recommendations save to the Signal Library.
- **Signal Library** (`/signals`) — System + org-custom signals, composable packs, deployment wizard. Validity windows (`valid_from`/`deprecated_at`/`superseded_by_signal_id` on `signals`, lighter `valid_from`/`deprecated_at` pair on `signal_packs`) mark a deprecated/sunsetting entry — sunset badge on `SignalCard`, "show deprecated" toggle on `SignalLibraryPage` (hidden by default).
- **Signal Enrichment Configuration** — Per-client identity mapping + per-deployment signal field mapping, composite 0–100 score, 12-rule validation engine, injected into the CAPI pipeline (non-fatal). Configured via `IdentityConfigStep` (ClientSetupWizard/ClientDetailPage) and `SignalEnrichmentStep` (DeploymentWizard).
- **Conversion Strategy Gate** (`/planning/strategy`) — Multi-objective wizard; Claude verdicts (CONFIRM/AUGMENT/REPLACE) with governance tier + platform action types. PDF/web brief. Enforced as a dismissible frontend nudge (`StrategyGateGuard`) — the backend `strategyGate` middleware is a pass-through.
- **Platform Connections** — OAuth to Google Ads/Meta/GA4/GTM (manager/child/standalone), AES-256-GCM encrypted tokens, account discovery.
- **Platform Reconciliation** — Config/volume/delivery diffs against connected platforms, severity-tracked findings, per-client tolerance config. `platform_discontinuities` register (seeded with Meta's Mar 2026 click-through attribution redefinition, GA4's attribution-model narrowing) + `discontinuityDiff.ts` runs first in `reconciliationRunner.ts`'s `executeRun()`, so a discontinuity-shaped drift reads as annotated context rather than an unexplained anomaly.
- **Implementation Health Checks (IHC)** — GTM container snapshots, tag config rule checks, baseline + drift detection, alert preferences. GTM containers connect either by manual JSON upload or via a two-phase OAuth flow (`GET /gtm/callback` discovers the user's accounts/containers and caches pending encrypted credentials in Redis under a one-time ref; `POST /gtm/callback/finalize` persists the picked container), and a connected container can be deployed to as a draft workspace (`POST /gtm/deploy`).
- **Data Quality Monitoring (DQM)** — GTG path health probes, DMA poll state, sGTM reachability probe, success/match rate monitoring. Per-org alert delivery via email/Slack (`dqm_alert_preferences`, `dqmAlertDelivery.ts`); DQM alert severity + CAPI match quality/dedup rate also feed the org Dashboard's `ClientHealthList` (escalate-only — never silently downgrades an existing findings-based health level).
- **Bid Signal Enricher** — Customer Match audience push (Google DMA) + LinkedIn Matched Audiences as a second destination (reuses the org's existing LinkedIn CAPI credentials, no separate OAuth; Google/LinkedIn destinations push independently since their APIs return incompatible result shapes), match-rate telemetry, agency-plan Data Manager Console.
- **Shopify Acquisition Channel** — Public Shopify App; install with no prior Atlas account, shadow Supabase Auth user provisioning auto-creates a full org via the existing `handle_new_user()` trigger; storefront ScriptTag auto-captures gclid/fbclid/wbraid/gbraid into order `note_attributes`; order/refund webhooks staged (`shopify_webhook_events`) then routed through a consent-gate-free `processServerSourcedEvent()` CAPI path (no live browser session to have captured real consent from); unauthenticated `/shopify/welcome` claim-your-account page.
- **Refund/Return Feedback** — `refund_events` tracking (Shopify webhook or manual `POST /api/refunds`); Google Ads gets automatic Customer Match audience removal plus a manual Conversion Adjustments CSV (`RESTATEMENT` w/ absolute `new_conversion_value` for partial refunds, `RETRACTION` for full); Meta is logged-only (no reversal API exists). `RefundsTab` in the CAPI Monitoring Dashboard.
- **Server-Side GTM (sGTM) Detection & Monitoring** — endpoint reachability verification (`client_platforms.is_verified`), per-client DQM health probe (`dqm_sgtm_checks`), IHC drift rule `SGTM_ROUTING_NOT_CONFIGURED`. Tag generation (routing GA4 traffic through the container) explicitly deferred pending GTM field-name verification.
- **Signal Tracking Dashboard** (`/signal-tracking`) — CAPI event log, filterable table, async CSV export, aggregate stat-card row (Total Signals / Avg Match Quality / Dedup Hit Rate / P95 Latency with period-over-period deltas).
- **Event Taxonomy** — System + org-custom event tree, platform mappings, full-text search. *(Backend route only — no frontend page yet.)*
- **Naming Conventions** — Org event/param naming rules, real-time validation + rename preview. *(Backend route only — no frontend page yet.)*
- **Crawl Signal Extractor (CSE)** — Subscription-gated site scan (`/crawl/:runId`); runs can be promoted to IHC baselines.
- **Usage Logging & Operator Monitoring** — Per-org usage logging, Browserbase nightly reconciliation, operator alerts (email/Slack).
- **Audit Engine** — Headless journey simulation, gap classification, scored PDF reports. Entry point is `EvaluateSiteCard` (Home + Dashboard); a bare-URL run can be linked to a client afterward (`audits.client_id` nullable).
- **Public No-Login Audit Scan** (`POST/GET /api/public/audit`, no `authMiddleware`, IP-rate-limited) — a URL-only scan through the *same* Check Register v2 pipeline authenticated scans use (`auditQueue` → `runAuditOrchestrator` → `journeySimulator` → `runRegister()`), not a separate lightweight checker. Scan Inputs are inferred from a zero-cost HTML fetch (`siteDetectionService`, `declaration_source: 'INFERRED_FROM_SITE'`) since a public visitor only supplies a URL. `audits.is_public`/`public_token` gate access to a 24h-TTL result; `POST /:token/email` captures an email for a lead notification + emailed report. Frontend: `PublicAuditPage`, `AuditReportCard`.
- **Check Register v2** (`rule_set_version: 'v2'`, `backend/src/services/validation/register/`, `REGISTER_VERSION` currently `1.1.0`) — a 13-layer, rule-based validation engine superseding the v1 audit engine's hardcoded rule list. 95 rules shipped across 12 rule layers (L0 Scope & Configuration → L10 Deduplication, plus L12 Hygiene & Integrity; L11 Reconciliation ships zero rules — greenlit 2026-09-13 as **disclosure-only** (rendered, never scored), design settled in `docs/ATLAS_L11_RECONCILIATION_SCOPING.md` §5/§6, not yet built). The score denominator is always the full 13-layer `ALL_V2_LAYERS` set — an untested layer is labelled `not_applicable` or `not_scanned`, never silently dropped from the fraction. Every rule carries an `evidence_class` (`DIRECT`/`INFERRED`/`DERIVED`/`PRESENCE`/`PRESENCE_INVERSE`) and resolves through a verdict lattice (`observation_confidence` → `PASS`/`FAIL`/`NOT_OBSERVED`/`INCONCLUSIVE`/`CONFLICT`, with severity ceilings on `PARTIAL`-confidence findings); only `PASS`/`FAIL` verdicts are scorable, and a layer needs ≥50% of its applicable-this-run rules resolved before it counts toward coverage (`MIN_CONFIRMED_RATIO`) — an under-covered run's composite score is withheld (`score_withheld_reason`) rather than averaged down. A run's `run_quality` (`COMPLETE`/`PROVISIONAL`/`INSUFFICIENT`, derived from settle/retry outcomes) gates client-facing export — `POST /:audit_id/export` returns 409 for `INSUFFICIENT` — without blocking the in-app report view. `outputLint.ts` hard-gates every v2 report's rendered narrative copy against a banned-word list before it ships (no absence claim rendered as certainty). `signalConsistency.ts`'s `CONF_01`–`CONF_05` cross-signal checker and `clickIdContention.ts`'s synthetic-multi-click-ID pre-filter both route affected findings to `could_not_be_assessed` instead of scoring a self-contradicting result; `signal_conflicts`/`rule_confirmations` tables persist conflicts and rescan-derived confirmations for future accuracy measurement. Scan Inputs (`site_type`, `declared_platforms`, `product_domain`/`checkout_domain`/`additional_properties`, `cmp`, `test_email`/`test_phone`, ...) drive `applies_to`/`platform_scope` applicability filtering and `requires` preconditions (a rule needing a page the crawl never reached is `skipped`, not `fail`). `step_coverage` tracks per-step URL provenance and whether navigation reached a page genuinely distinct from landing (a `heuristic`-sourced guess must now verify HTTP 2xx before counting); `stepUrlResolver.ts` fills `url_map` gaps via sitemap/robots.txt/link-harvest/path-heuristics (SSRF-validated, never overrides a user-supplied URL); `coverage_fingerprint` suppresses false regression alerts when the set of pages a scheduled re-scan happens to visit changes between runs; `collectDeep`/`evaluateAcrossFrames` (`dataCapture.ts`) pierce iframes and open shadow DOM for the two DOM-read call sites (outbound cross-domain link scan, GTM container-ID script scan) so a hosted checkout widget's tags/links aren't structurally invisible. Full sprint-by-sprint breakdown in `docs/atlas-sprint-plan-site-eval-coverage.md` (coverage/honesty work) and `docs/atlas-sprint-plan-pre-connection-confidence-tiering.md` (evidence-class/verdict-lattice/scoring-gate work).
- **Campaign Signal Validator** — Pre-flight diagnostic scoring whether a client's tracking can actually validate a given campaign, from a site scan + Journey Builder stage data (event-verdict heuristic). Ships as both an in-app surface (`ClientDetailPage` tab + Home promo card) and a standalone paid product (`/api/campaign-signal-validator`: public landing/result pages, one-time Stripe Checkout reusing the existing billing webhook for fulfilment, lean PDF report) for a prospect with no Atlas account.
- **Home Page** (`/`) — Branches on org existence: `FirstTimeSetup` vs `ReturningUserLanding` (`EvaluateSiteCard` / `QuickClientIntake`, `StatsRow`, `RecentActivityFeed`).
- **Operator Console Design System** — Orbitron/Rajdhani/JetBrains Mono type (`font-display`/`font-heading`/`font-mono`) + `console.*` Tailwind palette layered onto navy/severity tokens. Live across Sidebar, TopBar, OrgSwitcher, Home, main Dashboard, Signal Tracking Dashboard, and Planning Wizard Step 1. Sidebar nav is grouped into 7 sections (Workspace/Engine/Library/Implementation/Tracking/Advanced/Privacy); sidebar header is a plain "ATLAS" text wordmark — no icon mark (illegible at sidebar scale).
- **Health Dashboard** — Live health score, alert feed, historical trend, AIR `InsightsFeedPanel` (narrated cross-channel anomaly insights).
- **Auto-Insight Reporter (AIR)** — Nightly per-org metric ingestion from GA4/Google Ads/Meta Ads/LinkedIn Ads/Klaviyo (`services/air/ingestion/`, one connector per source, all writing to `air_metric_snapshots`) → anomaly detection against a rolling baseline (`anomalyDetector.ts`, `air_anomalies`, severity low/medium/high) → correlation against Atlas-internal signals within a ±3-day window (`correlationEngine.ts`, `air_insight_correlations`) → Claude-narrated insights (`narratorService.ts`, `air_insights`). Deliberately never blends revenue across channels — each source's figure stays its own independent series, and a Klaviyo (email) anomaly explicitly notes its revenue attribution may overlap with what other channels independently claim credit for. Surfaced via `GET /api/insights` (`pro` plan+) in `InsightsFeedPanel`. LinkedIn Ads' connector is wired but runs as a no-op today — no LinkedIn OAuth connect flow yet populates a `platform='linkedin'` connection row.
- **Channel Insights** — Session ingestion + diagnostic engine.
- **Consent Integration Hub** — JS banner + CMP sync (OneTrust/Cookiebot/Usercentrics), Google Consent Mode v2, Global Privacy Control (GPC) detection read fresh on every page load (production banner script + framework-agnostic `consent-engine.ts`) — hard-blocks the banner re-prompt by default (`gpc_hard_block`, per-org configurable) while GPC honouring itself stays unconditional; a GPC denial writes a `consent_blocked` `capi_events` row via the existing CAPI consent gate.
- **Realtime CAPI** — Providers: Meta/Google/LinkedIn/TikTok/Amazon/Microsoft/OpenAI all have live delivery services (`services/capi/*Delivery.ts`); Snapchat is declared in the `CAPIProvider` type but has no delivery service yet. Microsoft (UET + Conversions API) uses a best-effort endpoint path pending confirmation against Microsoft's docs (flagged in-file); OpenAI (ChatGPT Ads) delivers to `bzr.openai.com/v1/events`, instrumentation/dedup only, no incrementality claims. SHA-256 hashing, dedup, consent gating; new-vs-returning customer signal (Google Ads/GA4 via DMA `userProperties.customerType`, sourced from GTM cookie/dataLayer or Shopify `customer.orders_count`). TikTok Events API delivery (`tiktokDelivery.ts`) is wired into the pipeline, credential validation, and test-event flow; matches on hashed PII plus `ttclid` (captured alongside gclid/fbclid/wbraid/gbraid). LinkedIn also has qualified-lead conversion routing (`conversion_routes` — MAX/MARKETING/SALES_QUALIFIED_LEAD, routed per Atlas event name), IP-based identifiers (`SHA256_IP_ADDRESS`/`PLAINTEXT_IP_ADDRESS`/`GOOGLE_AID`), and multi-account conversion discovery (`listLinkedInConversions`, `GET /providers/:id/linkedin/conversions`).
- **Offline Conversions** — CSV upload → Google Data Manager API (`events:ingest`), async Bull queue, per-row error reporting. (Legacy `uploadClickConversions` — already migrated off, ahead of Google's June 2026 cutoff for that service.)
- **Organisation & Client Management** — Multi-tenant workspace, org switching, member roles.
- **Billing & Subscriptions** — Stripe Checkout + Billing Portal. Plans: `free`/`pro`/`agency` via `planGuard`/`<PlanGate>`.

## Key Technical Decisions

1. **Vite + React 19, not Next.js** — pure SPA, React Router v6, no server components.
2. **Express.js backend** — all API logic in `backend/src/`. Not Supabase Edge Functions.
3. **Bull + Redis** — audits, CAPI delivery, offline uploads, signal CSV exports run as Bull jobs.
4. **Credentials encrypted at rest** — `capi_providers.credentials`, `platform_connections.oauth_tokens`, and `gtm_container_connections.oauth_credentials_encrypted` all use AES-256-GCM via `@noble/ciphers`. Never log decrypted credentials.
5. **No PII in job payloads** — queue payloads contain only IDs. Raw PII nulled post-upload.
6. **Claude API calls are backend-only** — `ANTHROPIC_API_KEY` never exposed to the browser.
7. **Stripe billing** — Checkout Sessions and Billing Portal only. Webhook handler uses `express.raw()` mounted before `express.json()`.
8. **Plan hierarchy** — `free < pro < agency`. `planGuard(minPlan)` on backend, `<PlanGate minPlan="...">` on frontend. Super admins bypass both.
9. **Migration guards** — `ALTER TABLE` on optional tables must be wrapped in `DO $$ IF EXISTS (SELECT FROM pg_tables ...) THEN ... END IF; END $$` to survive Supabase preview environments.
10. **org_id resolution** — `req.user` carries only `id`, `email`, `plan`, `isSuperAdmin`. Resolve `organization_id` via `supabaseAdmin.from('profiles').select('organization_id').eq('id', userId)`. Note: some newer tables use `org_id` column (enricher_runs, dqm_*, audience_member_uploads) — match the column name used in that migration.
11. **shadcn/ui registry** — if `npx shadcn add` fails, install the Radix primitive directly and create the component manually (the Radix package is often already a dependency even when the wrapper isn't — check `package.json` first).
12. **Strategy Gate is a frontend nudge, not a backend block** — the `strategyGate` middleware (`backend/src/api/middleware/strategyGate.ts`) is a pass-through on its existing routes (`POST /api/planning/sessions`, client deploy); the brief requirement is enforced only via the dismissible `StrategyGateGuard` banner in the frontend.
13. **Operator console tokens over hardcoded hex** — new/touched frontend UI should use `console.*`/`severity.*`/`navy.*` Tailwind tokens and `font-display`/`font-heading`/`font-mono` (defined in `tailwind.config.js`) rather than raw hex literals or default shadcn muted-foreground/border tokens. Several pages (Dashboard, Signal Tracking Dashboard, Planning Wizard) still had hex literals until the operator-console rollout — grep for `#[0-9A-Fa-f]{3,6}` in a file before styling it to catch leftovers.
14. **Verify third-party API schemas against their live source before trusting existing types** — Atlas's Google Data Manager API integration had drifted materially from the live schema (wrong event shape, consent enum values, destination structure, audience-endpoint URL casing) until a fix shipped alongside the Shopify click-ID/new-customer signal work. Verified by fetching `https://datamanager.googleapis.com/$discovery/rest?version=v1` directly rather than relying on training-data assumptions. Re-verify before extending `dmaTypes.ts`/`dmaEventBuilder.ts` further.
15. **Server-sourced CAPI events use `processServerSourcedEvent()`** (`backend/src/services/capi/pipeline.ts`) — a narrow, explicit exception to the consent gate for integrations with no live browser session to have captured a real consent decision from (e.g. Shopify order/refund webhooks). Never default `consent_state` to `'granted'` for a live-browser pipeline call; this path is only for genuinely server-sourced events.
16. **Check Register v2 rules stay pure and synchronous** — a rule's `test(auditData)` never awaits or hits the DB. Anything needing an async lookup (`sgtmVerified`, `connected_gtm_container_id`, `product_domain_reachable`, the naming convention, resolved step-URL sources) is resolved by the orchestrator/`journeySimulator.ts` *before* `runRegister()` runs and read synchronously off `AuditData` — the "resolve outside, read inside" pattern used throughout `services/validation/register/`. A rule tagged `requires: ['conversion_surface']` is `skipped`, not `fail`, when its precondition is unmet (`scoring.ts` already excludes `skipped` from every denominator) — this is what stops a homepage-only scan from scoring as if every page had actually been checked.
17. **`REGISTER_VERSION` must bump whenever rule shape changes** (new required `ValidationRule` fields, a rule split, etc. — currently `1.1.0`) per its documented contract (Report Correctness Programme Part D4); it's stamped on every v2 report/audit row and read by the regression comparator to flag a denominator/version change across compared runs rather than silently misattributing a score jump to remediation.
18. **Absence is never asserted as certainty in rendered copy** — an `INFERRED`/`DERIVED`-class finding's evidence must read as "not observed" rather than "missing"/"broken" (`outputLint.ts` hard-gates every v2 report on this before it ships). This is a direct lesson from the Report Correctness Programme's Part B: a v1-era rendering dict silently intercepted some v2 `rule_id`s by name-collision, producing inconsistent copy across sibling rules from the same factory — the gate now scans the fully-assembled `ReportJSON`, not any single rendering code path.
19. **A `could_not_be_assessed` producer needs a `kind`, not a bespoke bucket** — `clickIdContention.ts`, `signalConsistency.ts`'s `partitionSignalConflicts()`, `coverageSuppression.ts`, and `degradationSuppression.ts` all route into the same `UnassessableFinding{rule_id, step, reason, kind}` type (`CONFLICT` for contention/cross-signal disagreement, `NOT_OBSERVED` for coverage/degradation). Adding a new suppression mechanism should extend this type, not invent a parallel one.
20. **`rule_confirmations`' re-scan comparator is deliberately one-directional** — a rule that failed on the previous v2 audit and passes on this one writes `CONFIRMED`/`rescan`; `REFUTED` is never auto-written by the comparator, since two scan results alone can't distinguish "the site genuinely changed" from "the original finding was simply wrong" — that needs a human (`client_answer`/`operator` source) to say nothing changed. No accuracy figure is computed or published from this data yet (deliberately, per its PRD) — don't wire one in without checking the sample-size reasoning in `docs/prd/pre-connection-scan-confidence-tiering.md` §15 first.
21. **A migration's tracked `version` is the leading digit run of its filename, and the ledger must match it exactly** — `supabase_migrations.schema_migrations.version` for `20260915001_meta_refund_signal.sql` is `20260915001` (digits up to the first underscore), with the remainder in `name`. Supabase's branching check compares *only* these version strings against the files in `supabase/migrations/`; any ledger row whose version doesn't correspond to a real file fails every preview deploy with `Remote migration versions not found in local migrations directory` — a message that names no offending row, so it reads as unrelated to migrations you just wrote. This repo's ledger had drifted into four distinct failure shapes at once (CLI-generated timestamps, whole-filename-as-version legacy rows, duplicates of the same migration under two versions, and applied-but-never-tracked migrations), all repaired 2026-09-13. **To diagnose:** diff production's ledger against a healthy preview branch's own `schema_migrations` — a preview branch is built by the CLI parsing the files directly, so its table *is* the ground truth for what each version should be. Note also that a branch's stored `status` is sticky (`main` read `MIGRATIONS_FAILED` from a stale run, and its `updated_at` never refreshes), and that `rebase_branch` kept replaying a stale failure after the ledger was verified correct — `reset_branch` is what actually rebuilt the preview. **Never name a new migration `YYYYMMDD_NNN_name.sql`** (underscore after the date) — that yields an 8-digit version which, alongside a same-day `YYYYMMDDNNN_name.sql`, is a *prefix* of it, and that combination breaks every Supabase deploy via CLI bug [supabase/cli#6036](https://github.com/supabase/cli/issues/6036): `FindPendingMigrations` sorts the remote list by version (`ORDER BY version`) but the local list by filename (`fs.ReadDir`), and since `'0'` (0x30) < `'_'` (0x5F) the two orders invert, so the shorter version is misreported as absent locally. Use `YYYYMMDDNNN_name.sql` (this repo's dominant form) or Supabase's standard 14-digit `YYYYMMDDHHMMSS_name.sql`. The five collisions this repo had were cleared 2026-09-13 by renaming four files and updating their ledger rows in lockstep — safe only because the CLI compares version strings and never checksums file contents, so a rename is invisible to it *provided* the ledger row moves with the file. Never rename a migration without updating its ledger row in the same change.
22. **Applying a migration via the Supabase MCP `apply_migration` tool records the wrong version** — it stamps its own 14-digit timestamp (e.g. `20260913162652`) rather than the version derived from the repo filename, which both desyncs the ledger and sorts wrongly against this repo's 8/11-digit scheme. This is the exact fingerprint of the historical drift found on 2026-09-13 (44 rows under auto-generated timestamps), so it is almost certainly how that drift accumulated. After any `apply_migration` call, `UPDATE supabase_migrations.schema_migrations SET version = '<filename version>', name = '<filename remainder>' WHERE version = '<generated>'`. Prefer letting the branching pipeline apply migrations on merge; reserve direct application for when that pipeline is broken.
23. **Google Ads API version lives in one place: `backend/src/integrations/google/adsApiVersion.ts`.** Before the Google Stack Alignment sprint plan's Sprint 1, five of the seven Google Ads REST call sites pinned `v18` and two pinned `v17` — both already sunset (v17 on 2025-06-04, v18 on 2025-08-20) — so every Google Ads API request had been failing for 12–15 months, not merely drifting toward a future cutover. Every call site now imports `GOOGLE_ADS_API_VERSION` from that one module (currently `v24`, sunsets May 2027) rather than hardcoding a version string; bump it there only. Distinct from Data Manager API versioning (`dmaTypes.ts` etc., decision §14) — Google Ads REST (account/config/read operations, GAQL) and Data Manager (offline conversion ingestion/delivery) are separate APIs with separate version lifecycles.

## Implementation Rules

1. **New tables** → `supabase/migrations/` as numbered `.sql` files. RLS required.
2. **Credentials** → encrypted with `@noble/ciphers` AES-256-GCM.
3. **No PII in logs or queue payloads.**
4. **Consent-first** — every event carries consent state.
5. **Zod validation** — all backend request bodies validated with Zod.
6. **Error boundaries** — wrap new pages in `SectionErrorBoundary`.
7. **Loading states** — every async op shows a skeleton or spinner.
8. **TypeScript strict** — `noUnusedLocals: true`, `noUnusedParameters: true`. Unused imports = build failure.
9. **Functional components only.** No class components. No `'use client'`.
10. **API responses** → `{ data, error, message }` shape.
11. **Zustand for client state.** No React Query or SWR.
12. **No fabricated UI data** — don't add charts, IDs, or status text that isn't backed by a real data source (e.g. a trend chart with no time-series endpoint behind it). Skip the visual rather than fake it, and note the gap.
